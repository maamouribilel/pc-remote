# Instructions for coding agents

These instructions apply to the whole repository. Read this file before changing the project. Claude must also read `CLAUDE.md`.

Current app version: `0.3.5`.
Current public release: [v0.3.5 preview](https://github.com/maamouribilel/windows-pc-mobile-controller/releases/tag/v0.3.5) — Windows companion plus experimental macOS ARM64/Intel and Ubuntu 24.04 x64 archives.

## Project and development

PC Remote is a Windows .NET/WPF tray companion serving a bundled TypeScript browser remote over HTTPS/WSS on a trusted Private LAN. Since 0.3.0, releases add experimental Avalonia companions for macOS and Ubuntu/GNOME built on the shared host. Use the pinned toolchain and existing scripts described in `README.md`. There is no cloud backend, database, or required `.env` file.

- Preserve PC-approved pairing, Windows user-bound credential protection, allowlisted commands, and input cleanup. Read `docs/protocol.md` before changing those paths.
- Document actual behavior and evidence. Keep historical evidence intact; add a dated entry for new work. Never claim recording-adapter tests prove physical iPhone use or execution of power actions.
- Keep dependencies, generated binaries, local settings, certificate exports, private keys, credentials, logs, and personal machine information out of Git. Release binaries belong in GitHub Release assets.
- Run checks appropriate to the change. Do not perform shutdown, restart, uninstall, or physical input tests against a user's active work without the required task authorization and disposable targets.
- Preserve separate HTTP budgets for unpaired peers and approved devices, plus reserved power-cancel/logout capacity. Recheck authentication and the original live session under the ownership lock after asynchronous request-body reads. Read `.github/SECURITY.md` for trust boundaries and private reporting.
- Certificates must pass strict chain/name validation and carry server AKI/SKI extensions. Renew legacy server leaves without replacing the trusted root or remembered devices. Do not resolve compatibility failures by disabling certificate verification.


## Portable backend, shared shell and platform development (Phases 1–5)

- Version 0.3.5 distributes the Windows WPF companion as the primary platform plus experimental macOS/Ubuntu archives of the shared shell. `PcController.Host` and `PcController.Core` target `net10.0`; WPF/UI and native Windows integration stay in App/Windows. Read `docs/portable-host.md` and the dated `MULTIPLATFORM_PLAN.md` execution log before continuing the migration.
- Shared host startup requires explicit `HostServices`; use `WindowsHostFactory` for the WPF companion. Keep DPAPI formats, ACLs, Schannel key loading, trusted roots and remembered devices intact. Certificate issuance/renewal is separate from OS key storage. Never substitute temporary test storage or recording adapters in production.
- Pointer/media/launcher preferences live in Host; Windows paths, discovery, shortcut/media key mappings and native APIs remain adapters. Preserve v1 wire semantics and the additive authenticated capability contract. The browser now consumes additive authenticated v1 capabilities/readiness; preserve independent action gating and Windows legacy compatibility.
- Use the pinned SDK 10.0.402 (runtime 10.0.13, updated 2026-10-13 for the .NET security release including CVE-2026-58280), Node 24.21.0 and npm 11.19.0. `python3 scripts/portable.py build`, `test`, `audit`, and `tls` support native macOS/Linux tools; strict TLS needs Python 3.13+. PowerShell 7 build/test automatically select portable projects off Windows; use `-Portable` on Windows. Keep the full Windows solution/regression job.
- Portable fixtures are test-project-only, loopback-only and temporary. Recording tests, container checks, cross-compilation and configured CI jobs cannot establish native input, DPAPI execution on Windows, physical-phone/LAN or installed-app acceptance. Record actual platform results and pending checks separately; do not start the next roadmap phase automatically.
- `PcController.Desktop` pins Avalonia 12.1.4 and retains the Windows WPF companion. Read `docs/desktop-shell.md`. macOS now composes real Quartz/Accessibility input and Keychain-backed storage, starts paused and requires explicit network approval. Linux has real XCB/XTEST, Remote Desktop portal and GNOME keyring source composition; real Ubuntu x64/GNOME X11 and Wayland acceptance remains pending. Read `docs/linux-setup.md`. Read `docs/macos-setup.md`. No test adapter/store may enter production composition.
- Network approval is explicit and session-only; invalidate it on connectivity/identity changes (macOS: network keys except Wi-Fi `LinkQuality` signal updates and `AirPort` record/field updates that keep the same joined network name, system sleep/wake, session switch, power-off), pause/release ownership and stop old LAN listeners before replacement. Space/full-screen, display and readiness (Secure Input/permission) transitions pause and release input but must not revoke LAN approval; pause-only transitions (Space, display, Secure Input, login screen, inactive session) must also keep the running host, its pairing link and pending pairing approvals, and the shell distinguishes a missing Accessibility permission (onboarding) from a transient session block, which the bridge reports as one named reason (`pc_session_state`); a failed system-wide focus query falls back to the frontmost application because permission is rechecked live before every post. Only an Accessibility permission or storage change rebuilds the capability snapshot. Validate platform identity/notification coverage before production LAN startup; certificate SANs must cover every exact binding. Do not infer trust from private addresses.
- Use `python3 scripts/portable.py desktop`, `desktop-test`, `desktop-fixture` (test-only), and `browser-capabilities`; PowerShell supports `test.ps1 -Desktop`. Run loopback HTTP suites sequentially on port 8443. Record native shell startup separately from headless/recording checks and native control. macOS uses its native bridge, per-user single-instance lock and lifecycle/storage readiness monitor. Linux source adapters retain Phase 4 native gates; do not call the Wayland gate complete from D-Bus/Xvfb evidence. Releases since 0.3.0 publish Phase 5 features as experimental previews; never describe them as stable platform parity or native acceptance. The macOS/Linux window follows the Windows dashboard (`docs/desktop-shell.md` window layout); keep its automation IDs stable and run `desktop-test` after UI changes. SIGTERM/SIGINT/SIGHUP, native Quit and OS logout use the same graceful Exit; only failed input cleanup cancels it.

- macOS native builds require Xcode Command Line Tools; `PcController.MacOS/native/bridge.m` uses public Quartz/Accessibility, Keychain and SystemConfiguration/AppKit APIs. Never use Windows key codes/wheel events or request Input Monitoring/Screen Recording/Location as a compatibility fallback. Keep Command-layout resolution and Unicode scalar handling. Text Input Source/keyboard-layout APIs may only run on the main thread (they trap off the main queue on current macOS); worker threads read the bridge's main-thread layout cache.
- Mac storage uses a non-syncing key in the default per-user file-based Keychain and path-authenticated AES-GCM envelopes under `~/Library/Application Support/PC Remote` (0700/0600, umask 077, no symlinks). Locked/missing/denied storage must stop listeners; missing keys/roots never silently reset installation trust. A changed ad-hoc code identity after an update is refused silently; only the explicit local **Allow Keychain access after update…** action may permit macOS's own Keychain dialog for the existing key. Never edit ACLs, unlock, create or replace keys in that path. Preserve Windows DPAPI formats. Event tracking survives listener replacement, and failed cleanup blocks Resume/graceful Exit.
- Run `scripts/portable.py mac-test`, `mac-storage`, and Python 3.13+ `mac-tls`; `mac-smoke` requires Accessibility and creates a guarded disposable Cocoa target. Abort test actions on target focus loss; permit only tracked up events for safety cleanup. Run all HTTP suites sequentially on 8443. Never relabel unavailable native/phone/lock/roaming/Intel acceptance as passed.
- `python3 scripts/package-macos.py` creates a new ignored version-aware provisional Apple Silicon `.app`/ZIP/checksum/manifest; `--rid osx-x64` builds the Intel bridge/runtime separately. `scripts/package-linux.py` requires Linux x64 and creates an Ubuntu self-contained archive. No Developer ID signature/notarization or distribution signature is claimed; only `--final` outputs from a clean tagged commit may become release assets. `scripts/sign-macos-local.py` re-signs an installed bundle with a per-Mac self-signed identity so the Accessibility entry survives updates (the Keychain partition list still names each build's cdhash, so that approval stays once per build); it is local-only, refuses `CI=true` and never produces release assets. Run `scripts/check-package.py --rid <rid>`; cross-build checks are separate from native startup. `--final` (packaging and `check-package.py`) produces release names/manifests only from a clean committed tree; the CI `workflow_dispatch` input `final` builds them on clean runners without tagging or publishing.



- Linux native builds require `cc`, `pkg-config`, GLib/GIO, libsecret, XCB/XTEST and libxkbcommon-x11 development packages. Runtime is unprivileged: actual logind session/backend, GNOME ScreenSaver, NetworkManager and session-bus observation are required. Wayland uses consented RemoteDesktop `Notify*` input, never XWayland/uinput/root fallback; no EIS/Notify mixing. Phase 5 media/volume/launcher/logind power/autostart use real native services; missing permission/services fail closed. Native runtime additionally needs libpulse/PulseAudio or PipeWire-Pulse.
- Linux storage requires the reviewed same-user GNOME provider, unlocked persistent login collection and encrypted restricted login-keyring format. Blank-password/plaintext, missing/locked/unsupported providers fail; Secret Service is not DPAPI-equivalent. Linux AES-GCM files use 0700/0600 and path AAD; preserve roots/devices and reject missing keys/roots. No fixture seam appears in the production bridge.
- Linux text is disabled until explicit local GTK Unicode opt-in. Preserve independent capabilities and target limits; do not claim universal Unicode or Wayland receipt from portal calls. Failed cleanup retains tracking and blocks Resume/Exit; interrupted compose or ended-backend tracking needs explicitly verified local recovery, never silent clearing or old ups in a replacement session.
- `scripts/portable.py linux-test`, `linux-x11`, `linux-portal`, `linux-storage` separate faults, private Xvfb/GTK (US/French), private fake-portal protocol and real disposable encrypted GNOME keyring/TLS. Python 3.13+ adds strict Linux storage TLS. Real Ubuntu x64/GNOME X11, Wayland text/cleanup, lock/suspend/roaming/tray and physical-phone/LAN gates remain pending. Run HTTP suites sequentially on 8443; Phase 4 remains In progress; Phase 5 implementation/candidate checks do not close native/manual gates.

## Phase 5 features and provisional release readiness

- Read `docs/release-readiness.md` and `docs/pc-features.md`. Mac Core Audio/system media keys and OS-specific focused player shortcuts, `.app` LaunchServices, SMAppService login registration and console-user IOKit sleep are source candidates. Mac restart/shutdown remain unavailable/backend-denied. No Automation/root/shell fallback is allowed.
- Linux uses native libpulse (PulseAudio/PipeWire-Pulse), unambiguous controllable MPRIS General playback, focused player shortcuts, restricted `.desktop` GIO/ELF launches, local GNOME XDG autostart and logind power only when `Can* == yes`, with `interactive=false` and a final permission/session recheck. Never enable challenge/unsupported actions or override inhibitors. Wrapper/interpreter/terminal/arbitrary-argument launchers are unsupported.
- Configured IDs remain the only launcher wire input; paths/arguments never arrive from the phone. Keep backend capability checks, v1 fields, session-bound single-use confirmation, 30-second cancellable countdown, final ownership/auth recheck and conservative cleanup. Recording/private-bus power tests never establish physical execution.
- Login opt-in uses a stable local installation and OS approval; starts paused, with fresh network approval and Wayland consent. Do not change the user's actual login registration during automated checks; use disposable XDG entries or fault adapters.
- Product version is shared in `Directory.Build.props` (`PcRemoteVersion`); Desktop inherits it, Windows' explicit project version must match. Update shared/Windows versions, Windows package default and installer fallback together only for an authorized new release. Provisional packages retain the current source version with candidate filenames, base revision/dirty-source digest, runtime/web/native/license inventories and SHA-256 sums. No nonexistent public links. Compare every actual archive member with the inspected inventory. Mac ZIPs retain only inventoried public code-signature attributes via copyfile, excluding local provenance/Finder/ACL data; verify the seal after extraction. Normalize Linux TAR ownership metadata.
- Run Release/shared/desktop/adapter/browser/strict-TLS checks, dependency audits, `scripts/audit-runtime.py`, release-doc synchronization, package contents/architecture/startup and source/artifact secret scans. HTTP suites stay sequential on 8443. Actual native player/audio/login/power, Windows execution, macOS Intel/signed/installed, real Ubuntu x64/GNOME X11/Wayland and phone/LAN gaps remain separately visible. CI configuration is not an observed run.
- Final publication still requires separate authorization, complete synchronization, all source/docs committed before rebuilding from that exact clean revision, new annotated tag, accurate preview assets/aggregate checksums and independent public URL/size/hash verification. Never publish or replace assets from a dirty provisional candidate.

## Mandatory release synchronization

**A new app version is not complete until its source, documentation, agent instructions, and GitHub release agree. Do not publish a binary-only update or report a release as complete while these updates are missing.** Follow `docs/releases.md` and `docs/release-checklist.md` for every release.

1. Choose a new three-component version. Update shared `PcRemoteVersion` in `Directory.Build.props`, verify Desktop inherits it, update `src/PcController.App/PcController.App.csproj`, the default in `scripts/package.ps1`, and the fallback in `installer/PCRemote.iss`. The private frontend package's `0.0.0` is not the distributed app version.
2. Update `README.md`: current version, preview/stable status, download badge, installer/ZIP/checksum links, release notes link, package commands and output names. Refresh features, requirements, setup, limitations, screenshots, and walkthrough when their behavior changes. Use real captures and preserve media provenance.
3. Update **both `AGENTS.md` and `CLAUDE.md`**: current version/release links and any changed build, test, architecture, security, or publishing instructions. Keep their shared instructions consistent.
4. Update `docs/releases.md` for the new downloads and publishing procedure. Add dated results and known gaps in `docs/release-evidence.md`. Review `docs/release-checklist.md`, setup, limitations, protocol, third-party notices, and implementation status; change them when affected. Do not relabel old evidence as new validation.
5. Review **`.github/` files** (workflows, pull request template, and any future release configuration) for the new version and process. Update affected GitHub files; do not leave stale version assumptions or broken automation. The pull request release checklist must be completed for version bumps.
6. Run `./scripts/check-release-docs.ps1`, Release build, default checks, `./scripts/test.ps1 -Security`, pairing, lifecycle, PC feature, browser checks, and `./scripts/test-certificate.ps1` (Python 3.13+ for strict TLS validation; provided in CI). Run `./scripts/audit-dependencies.ps1` and check advisories for the bundled runtime versions. Run applicable installed/native/LAN checks and record manual acceptance gaps accurately. Packaging calls the documentation check automatically. Verify installer/ZIP hashes, license notices, absence of debug symbols, and a secret scan of the source and distributable package.
7. Commit all corresponding source and documentation to `main` before final packaging and tagging, and run the `final` workflow dispatch on that commit: that single run is the release CI gate (every suite on every OS) and builds the Windows/macOS/Ubuntu assets. The workflow no longer runs on every push to `main`. Build final assets from that commit (the `final` workflow dispatch or `--final` scripts) so every informational source revision agrees with the release tag; provisional package tests may run earlier. Create an annotated `vX.Y.Z` tag pointing to that exact commit, and push `main` and the tag. Never move a published tag or replace its assets with a different build; use a new version.
8. Prepare the GitHub Release for that tag with accurate changes, requirements, checks, known limits, and installer, portable ZIP, any macOS/Ubuntu archives and manifests, and one combined `SHA256SUMS.txt`. Keep incomplete manual acceptance visible and use preview status when appropriate. Publish within the user's authorization; do not treat this file as standing permission for an otherwise unauthorized release.
9. After publication, verify the public tag/commit, release status, all download links, asset sizes, and SHA-256 digests against the local files. Check the README and release notes render correctly. Report the release URL, version, validation, and remaining limits only after verification.

The GitHub `Release documentation` workflow catches inconsistent version declarations and download links. It also checks that README, both agent files, download documentation, and release evidence changed when the app version changes. It does not replace runtime testing, secret scanning, or public asset verification.

For documentation-only maintenance, keep the existing release version and tag. Commit and push the documentation without rebuilding or replacing published assets.
